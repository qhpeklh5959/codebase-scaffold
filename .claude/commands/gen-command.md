为当前代码库生成定制化 command，或分析代码库后主动建议应该新增哪些 command。
用法：`/gen-command [<需求描述>] | --suggest | --list | --create <name>`

---

## 参数说明

- **无参数 / `--suggest`**：分析当前代码库和已有 commands，生成建议清单写入 `command-suggestions.md`
- **`--list`**：展示 `command-suggestions.md` 中的待处理建议，不做其他操作
- **`--create <name>`**：从 `command-suggestions.md` 中找到该名称的建议，生成对应的 command 文件
- **`<需求描述>`**：用户直接描述需求，跳过建议阶段，直接生成 command 文件

---

## 模式 A：自动建议（无参数 / `--suggest`）

### Step A-1：加载现有上下文

读取：
- `.agent/refs/CODEBASE.md` — 技术栈、目录结构、测试框架
- `.agent/refs/patterns.md` — 现有扩展模式
- `.agent/refs/conventions.md` — 编码规范
- `.claude/commands/` 目录 — 列出已有 commands（包括脚手架自带的和已生成的），明确哪些已经存在，避免重复建议
- `.agent/refs/command-suggestions.md` — 查看已有建议，避免重复

### Step A-2：识别建议机会

从以下几个维度分析，每个维度找出 1~3 个潜在 command：

**技术栈特定工作流**：根据 CODEBASE.md 中的技术栈，识别该栈下常见的高频任务。例如：
- Spring Boot → 生成 Controller/Service/Repository 三件套
- Django → 生成 migration、admin 注册
- React → 生成组件脚手架 + Storybook
- gRPC → 生成 proto + stub + handler 骨架

**代码库扩展模式**：从 patterns.md 中识别"添加新实现类"等步骤较多的模式，若超过 3 步，值得封装为 command。

**测试生成特化**：通用的 `/test-gen` 之外，是否有需要特殊处理的测试场景（如：集成测试、E2E 测试、性能基准测试）。

**构建 / 运维脚本**：是否有常用的多步操作（如：清理 + 构建 + 启动、数据库 migrate + seed）。

**代码规范检查**：根据 conventions.md，是否有可以自动检查规范遵守情况的场景。

### Step A-3：写入建议

将建议写入 `.agent/refs/command-suggestions.md`（追加，不覆盖已有记录）：

```markdown
## {name}（{来源：bootstrap 分析 / reflect 分析 / 用户需求}）
- **触发场景**: 描述什么时候会用到
- **解决的问题**: 目前没有这个 command 时，用户需要手动做什么
- **建议的步骤摘要**: 1. ... 2. ... 3. ...
- **依赖的 refs**: CODEBASE.md / patterns.md / ...
- **状态**: 待处理 | 已生成 | 已忽略
- **建议时间**: {今天日期}
```

### Step A-4：输出摘要

列出本次新增的建议（名称 + 一句话描述），提示用户：
- 运行 `/gen-command --list` 查看全部建议
- 运行 `/gen-command --create <name>` 生成某个 command

---

## 模式 B：从建议生成（`--create <name>`）

从 `command-suggestions.md` 找到对应名称的建议，读取其步骤摘要和依赖 refs，进入模式 C 的生成流程。

生成完成后，将该建议的状态更新为 `已生成`，并记录生成时间。

---

## 模式 C：直接生成（`<需求描述>`）

### Step C-1：理解需求

解析 `$ARGUMENTS` 中的需求描述，明确：
- 这个 command 要完成什么任务
- 触发场景（用户什么时候会用它）
- 需要哪些参数（目标路径、名称、选项等）

### Step C-2：检查重复

读取 `.claude/commands/` 目录中的已有 command 列表，判断是否已有功能高度重叠的 command：
- 若高度重叠：提示用户现有 command 是否满足需求，建议在已有 command 上扩展而非新建
- 若无重叠：继续

### Step C-3：加载代码库上下文

读取 CODEBASE.md、conventions.md、patterns.md，理解：
- 生成的 command 需要和哪些已有 refs 结合
- 代码库的技术栈决定了 command 的实现细节（如何查找文件、运行命令）

### Step C-4：生成 command 文件

**文件名**：从需求中提取简洁的英文 kebab-case 名称（如 `gen-controller.md`、`run-migration.md`）

**文件路径**：`.claude/commands/{name}.md`

**文件结构**（必须遵循以下模板，保持与脚手架内置 commands 一致的质量）：

```
<!-- Generated by /gen-command | codebase: {CODEBASE.md中的项目名} | date: {今天日期} -->

{一句话描述，说明做什么。用法：`/{name} <参数说明>`}

---

## Step 1：加载上下文

读取 {列出需要的 refs 文件} ...

## Step 2：{主要步骤}

...

## Step N：更新 failures.md（积累经验）

若执行过程中遇到问题，追加到 failures.md：

{错误类型} / {根因} / {修正方式}

## 完成输出

- {输出项1}
- {输出项2}

## 重试规则（若适用）

若执行失败：1. 解析错误 2. 查阅 failures.md 3. 修正后重试，最多 3 次
```

**生成要求**：
- 每个 Step 有明确的操作指令，不写模糊描述
- 读取代码库上下文的步骤放在最前面
- 生成代码的步骤必须引用 conventions.md 的规范
- 末尾必须有 failures.md 更新步骤（积累经验）
- 参数通过 `$ARGUMENTS` 传入，在 Step 1 中解析

### Step C-5：确认并写入

输出生成的 command 内容，说明：
- 文件路径
- 用法示例
- 依赖的 refs

确认后使用 Write 写入文件。

---

## 生成后的维护

- 生成的 command 和内置 command 完全等价，可以被 `/reflect` 识别并更新
- 若生成的 command 在使用中发现问题，`/reflect` 会将经验记录到 failures.md，下次生成同类 command 时可参考
- 若某个生成的 command 不再需要，直接删除文件即可
