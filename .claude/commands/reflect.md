根据近期任务经验，主动更新知识库，提升后续任务质量。用法：`/reflect [可选：说明本次要更新的内容]`

---

## 触发时机

以下情况建议运行 `/reflect`：

- 完成一次 `/extend` 或 `/test-gen` 之后（无论是否经历了重试）
- 发现生成的代码与代码库风格不符时
- 手动修正了 Agent 生成的代码之后
- 代码库新增了重要模块或发生了重构之后

## Step 1：回顾近期任务

回顾当前会话中执行过的任务，提取：

- 用了哪些 refs 信息
- 哪些信息**用上了但发现有误**（导致重试或需要手动修正）
- 哪些信息**缺失**（在 refs 中找不到，只能现场推断）
- 哪些信息**冗余**（在 refs 中记录了但从未用到）

若 $ARGUMENTS 有额外说明，优先处理用户指出的方向。

## Step 2：更新 failures.md

对每次重试或失败：

1. 确认是否已记录在 failures.md 中
2. 若已记录，检查描述是否准确，必要时补充修正方式
3. 若未记录，按格式新增：

```
## [错误类型]
- 现象：
- 根因：
- 修正方式：
- 相关 refs 修正：
```

同类错误合并，不重复记录。

## Step 3：更新 conventions.md / patterns.md

若发现有遗漏的规范或模式：

- 新增规则时，附上来源（代码文件路径），说明这条规则的依据
- 修正错误规则时，注明之前的错误内容，避免未来混淆
- 删除从未用到且可能造成误导的规则

## Step 4：更新 symbols.md

若代码库中新增了重要的类/接口，或发现已有记录的路径/签名过时：

- 新增符号时，遵循已有格式
- 更新路径时，保留旧路径的注释（`// 旧路径，已迁移`），持续一个版本

更新完成后，检查所有被修改的 refs 文件是否超过 200 行；若超过，按 CLAUDE.md 中的拆分规则拆分，将原文件改为索引。

## Step 5：评估 CODEBASE.md

检查入口文档是否仍然准确：

- 目录结构有变化？更新对应描述
- 新增了关键扩展点？在扩展点索引中补充
- 测试运行命令有变？更新

## Step 5.5：更新依赖描述（若有）

若本次任务使用了 `.agent/refs/deps/` 下的依赖知识，检查：

- deps 中记录的符号签名是否仍准确（依赖库可能升级）
- 本库使用了新的依赖符号但 deps 中尚未记录？追加到对应 `deps/{name}/symbols.md`
- 若依赖库有重大变化，提示用户重新运行 `/import-dep {name} --refresh`

## Step 5.6：识别 command 自动化机会

回顾本次任务，判断是否存在值得封装为定制 command 的模式：

触发条件（满足任意一条即建议）：
- 本次任务需要手动执行超过 3 个步骤，且下次遇到类似场景还会重复
- 使用了某个现有 command 但需要配合额外手动操作才能完成
- 遇到了当前 commands 覆盖不到的场景（如特定的代码生成模式、特定的调试流程）
- 本次 failures.md 新增了某类错误，该错误有固定的解决流程可以自动化

若触发，读取 `.agent/refs/command-suggestions.md`，检查是否已有类似建议（避免重复）：
- 若无：追加新建议（格式同 `command-suggestions.md` 模板）
- 若已有：更新该建议的描述，补充本次观察

在输出摘要中列出新增的建议（若有）。

## Step 6：输出更新摘要

```
## reflect 更新摘要

### 修正的内容
- conventions.md: 补充了 XX 规范（原因：...）
- patterns.md: 修正了 XX 步骤（原因：...）

### 新增的内容
- symbols.md: 新增 XX 类（来源：...）
- failures.md: 新增 XX 错误类型

### 清理的内容
- 删除了 XX 冗余规则

### 新增 command 建议（若有）
- {name}: {一句话描述}（运行 /gen-command --create {name} 生成）

### 仍存在的不确定项
- （列出无法通过静态分析确认的内容，需用户确认）
```
