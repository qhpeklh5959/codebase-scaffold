# 陪跑开发

在实现任务时，以计划与 checklist 先行，并同步可复用的代码库知识。用法：`$companion <开发任务>`。

## Step 0：确定工作区与隔离边界

- 若根目录有 `AGENT-DEVELOPMENT.md`，进入**自我维护模式**：计划、checklist、进度和复盘只能写入 `.agent/self/companion-{task-slug}.md`；其中的知识结论只适用于当前 agent 开发，不能写入可部署模板或普通 `.agent/refs/`。
- 否则进入**业务代码库模式**：创建 `.agent/work/{task-slug}.md`。该文件是任务状态，不是长期知识库；可在任务结束后保留作审计记录。
- 先读取 `CODEBASE.md`、与任务相关的 symbols/patterns/conventions、`failures.md`；可能涉及遮蔽目标时检查 `shadow-state.md` Active 节。
- 业务库 bootstrap 生成的 `CODEBASE.md` 会重复说明该分层；若两者不一致，以本工作流和 `AGENTS.md` 的维护规则为准并在本次任务中修正目标库的 refs。

## Step 1：先写计划与验收条件

在修改实现文件前创建任务文档，至少包含：

```markdown
# {任务标题}
## 目标与非目标
## 已知事实与待确认项
## 实施计划
## Checklist
- [ ] …
## 验证记录
## 知识库同步记录
```

- 将任务拆成可验证的小步骤；标注可能受影响的文件与接口。
- 计划、checklist、验证日志和未确认项都先写入 task work 文档，不要为了“同步”直接写入 refs。
- 对会明显改变范围的未知项，先向用户确认，不将推测作为事实写入 refs。
- 实施前在对话中简要展示计划与首个 checklist；用户明确要求直接实现时，可在展示后继续，不必等待再次确认。

## Step 2：按 checklist 实施

每完成一个有意义的步骤：

1. 将 checklist 从 `[ ]` 更新为 `[-]` 或 `[x]`，写明实际变更和验证状态。
2. 发现可复用且已由代码、测试或配置验证的事实时，立即同步到相应 refs，并附相对路径和行号。
3. 临时假设、进行中的排查和未验证结论只写入任务文档的“待确认项”，不要写入 refs。
4. 遇到失败时按 `AGENTS.md` 查询并更新 `failures.md`，再遵守三次重试上限。

## Step 3：持续检查

- 在跨模块修改、接口调整或测试失败后，重新检查计划是否仍覆盖实际范围；范围变化时更新“目标与非目标”和 checklist。
- 每次开始新步骤前，读取刚更新的任务文档，避免实现状态与文档脱节。
- 长任务至少在每个阶段完成时向用户报告已完成 checklist、待确认项和下一步。

## Step 4：验证与收尾

1. 运行与改动相称的构建、测试或静态检查，并将命令和结果写入“验证记录”。
2. 对失败、未运行的验证或未覆盖路径如实标注；不要以未验证状态关闭任务。
3. 复核 refs 只包含可复用的已验证结论，任务文档保留过程性信息。
4. 将完成项标为 `[x]`，未完成项保留并解释原因；输出变更、验证、refs 同步和遗留项摘要。
